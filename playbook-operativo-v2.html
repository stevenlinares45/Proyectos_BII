Metodología de trabajo: los 8 pasos de cualquier proyecto

Un proyecto de datos no empieza con código: empieza con una pregunta de negocio. Estos 8 pasos te dan un camino repetible desde el primer día.

Objetivo

Tener una metodología clara que apliques a cualquier proyecto, sin improvisar. Saber exactamente qué hacer en cada momento y qué entregable dejar antes de pasar al siguiente paso.

SQL para Ingeniería de Datos

El lenguaje que transforma datos en decisiones. No necesitás ser experto: necesitás dominar los 5 patrones que usás todos los días.

Objetivo

Dominar SQL desde cero hasta los patrones profesionales: consultar, unir, organizar en pasos, operar dentro de grupos y cargar sin duplicar. Todo con ejemplos reales de pipelines.

01 Fundamentos: las 6 cláusulas que lo hacen todo

CláusulaQué haceEjemplo
SELECTElegir columnasSELECT nombre, precio
FROMDe qué tablaFROM ventas
WHEREFiltrar filasWHERE fecha > '2024-01-01'
GROUP BYAgrupar para resumirGROUP BY mes
ORDER BYOrdenar resultadosORDER BY total DESC
LIMITVer solo N filasLIMIT 100
Regla de oro El orden de ejecución lógico es: FROM → WHERE → GROUP BY → SELECT → ORDER BY → LIMIT. El motor filtra antes de agrupar, y agrupa antes de ordenar.

02 JOIN: unir tablas sin perder ni multiplicar datos

Los JOIN combinan tablas por una columna en común. Elegir el JOIN equivocado es la causa #1 de números incorrectos en dashboards.

JOINQué devuelveCuándo usarlo
INNER JOINSolo filas que existen en AMBAS tablasQuerés solo los registros que tienen match (ej: ventas con cliente válido)
LEFT JOIN DefaultTodo de la izquierda + match de la derecha (NULL si no hay)Conservar todos los hechos aunque falte la dimensión. En data warehousing es el estándar.
RIGHT JOINTodo de la derecha + match de la izquierdaRaramente usado. Preferí LEFT JOIN y cambiar el orden de las tablas.
FULL OUTER JOINTodo de ambas tablas, con NULL donde no hay matchComparar dos fuentes: "¿qué está en A pero no en B?"
CROSS JOINProducto cartesiano: cada fila de A con cada fila de BGenerar combinaciones (ej: todos los productos × todos los meses). Cuidado: explota el volumen.
Error costoso #1 Usar INNER JOIN entre una fact y una dimensión. Si la dimensión no tiene un producto nuevo, esas ventas desaparecen del resultado y el total de ventas baja sin explicación. Siempre LEFT JOIN desde la fact hacia las dimensiones.

03 CTEs: organizar el pensamiento en pasos

Una CTE (Common Table Expression) es una tabla temporal con nombre, definida con WITH. Te permite dividir una query compleja en pasos legibles.

Ventaja clave Sin CTEs, esta query sería una subquery anidada de 4 niveles. Con CTEs, cada paso tiene nombre y se lee de arriba hacia abajo, como un pipeline.

04 Window Functions: operar dentro del grupo sin perder filas

Las Window Functions calculan algo sobre un grupo de filas sin colapsarlas. A diferencia de GROUP BY, cada fila sigue existiendo en el resultado.

Necesitás...UsáEjemplo
Deduplicar (quedarte con 1)ROW_NUMBER()OVER(PARTITION BY id ORDER BY ts DESC)
Ranking con huecosRANK()OVER(ORDER BY ventas DESC) → 1,2,2,4
Ranking sin huecosDENSE_RANK()OVER(ORDER BY ventas DESC) → 1,2,2,3
Valor del período anteriorLAG(monto,1)OVER(PARTITION BY zona ORDER BY mes)
Valor del período siguienteLEAD(monto,1)OVER(PARTITION BY zona ORDER BY mes)
Acumulado corrienteSUM(monto) OVER(ORDER BY fecha ROWS UNBOUNDED PRECEDING)

Metodología Git y GitHub
Fundamentos

Git y GitHub para Data Engineers

Tu código no existe hasta que está versionado. Git es el seguro de tu trabajo: te permite experimentar sin miedo, colaborar sin pisarte y volver atrás cuando algo se rompe.

Objetivo

Versionar todo el código SQL, notebooks y configuración de pipelines. Trabajar en equipo sin sobrescribir el trabajo de otros. Mantener un historial claro de qué cambió y por qué.

01 Qué es Git y por qué lo usás todos los días

Git es un sistema de control de versiones distribuido. Guarda una foto de tu código cada vez que hacés un commit, permitiéndote:

  • Volver atrás si un cambio rompió algo.
  • Trabajar en paralelo con otros sin conflictos.
  • Saber quién cambió qué y cuándo: fundamental en auditorías.
  • Revisar código antes de que llegue a producción.
Regla de oro en datos Si no está en Git, no existe. Un notebook que corre solo en tu máquina es un riesgo, no un activo. Commiteá al finalizar cada tarea lógica.

07 Versionado: tags para marcar releases

Buenas prácticas
  • Commits atómicos: un commit = un cambio lógico. No mezclar "fix SQL + update README + cambiar color".
  • .gitignore obligatorio: credenciales, datos (.csv, .parquet), caches, entornos virtuales.
  • Nunca commitees a main directamente. Siempre por PR con review.
  • Revisá los diffs antes de pushear. git diff --cached te muestra qué vas a commitear.
  • Resolver conflictos localmente: no uses la UI de GitHub para conflictos complejos.
Errores comunes
  • "Subí todo junto al final" → commits gigantes imposibles de revisar. Commiteá al terminar cada tarea pequeña.
  • Commitear credenciales. Si pasa, rotá el token INMEDIATAMENTE y usá git filter-repo o BFG para borrarlo del historial.
  • Mergear sin probar. Un PR aprobado no garantiza que funcione en staging. Corré los tests.
  • Ramas viejas sin borrar. Acumulan polvo y confusión. Borrá las feature branches después del merge.

03 Estructura de carpetas detallada

Convención de numeración El prefijo numérico (01_, 02_) define el orden de ejecución. Cuando abrís la carpeta en el IDE, los archivos aparecen en el orden correcto. No hay que adivinar qué corre primero.
Buenas prácticas
  • README primero, código después. Si no podés explicar qué hace, no sabés qué estás construyendo.
  • Un notebook = una tabla destino. Facilita depurar y orquestar.
  • Separá configuración de código. Las credenciales y rutas van en variables, no hardcodeadas.
  • Documentá las decisiones. Cada ADR explica por qué se eligió X sobre Y. En 3 meses nadie se acuerda.

Entender el problema y traducirlo a requerimientos técnicos

El 80% de los proyectos que fallan, fallan acá: se empieza a codear sin saber qué decisión de negocio va a alimentar la tabla.

Objetivo del tema

Convertir un pedido difuso ("necesito un dashboard de ventas") en un documento técnico accionable: métricas, granularidad, fuentes, frecuencia y criterio de aceptación.

Contexto de negocio

Quien te pide el proyecto casi nunca habla en términos de datos. Habla de un problema: "no llegamos al target", "no sabemos qué productos rotan". Tu trabajo en esta fase es hacer de traductor: del problema al modelo de datos que lo responde.

01 Las 7 preguntas que siempre tenés que responder

#PreguntaQué define
1¿Qué decisión se toma con estos datos?Si no hay decisión, no hay proyecto
2¿Cuál es la métrica principal (KPI) y su fórmula?Las columnas de la tabla de hechos
3¿A qué nivel de detalle? (grano)Una fila = ¿qué? Define todo el modelo
4¿Por qué dimensiones se va a filtrar?Las tablas de dimensión
5¿De dónde salen los datos y quién los mantiene?La ingesta y los riesgos de calidad
6¿Cada cuánto se actualiza? ¿Qué latencia acepta?La estrategia de carga y la orquestación
7¿Cómo sabremos que está bien?Las validaciones de la Fase 4

02 Traducir del negocio a lo técnico

Dice el negocioSignifica técnicamente
"Quiero ver el rendimiento por turno"Grano = operario × hora; dimensión tiempo con turno
"Necesito compararlo contra el objetivo"La fact necesita valor_real y valor_target
"Que se actualice durante el turno"Carga incremental horaria, no full diaria
"Quiero saber por qué bajó"Conservar las dimensiones causales (% mixto, backlog)
"El mes pasado el dato estaba mal"Historización (SCD2) o reproceso por partición
Mercado LibreDashboard de control operativo — Inbound

Pedido original: "necesitamos ver el UPH del turno".

Lo que faltaba preguntar: ¿UPH contra qué target? El target fijo (45) no servía porque el % de carga mixta cambia la capacidad real. Sin esa pregunta, el dashboard mostraría "-15% vs target" sin explicar nada — el equipo parecería estar fallando cuando en realidad superaba el target ajustado.

Requerimiento resultante: grano = hora × turno; métricas uph_real, uph_target_base, uph_target_ajustado (calculado con % mixto), backlog; actualización horaria; criterio de aceptación: el target ajustado reconcilia con la fórmula operativa.

Fase 1 · Diseño

Diseñar la arquitectura en capas

Organizar el flujo desde el dato crudo hasta la tabla que consume el negocio, de forma que sea auditable, reprocesable y no se rompa.

Objetivo del tema

Definir qué capas vas a tener, qué entra en cada una y qué transformación ocurre entre ellas — para que cualquier persona (vos en 6 meses incluido) pueda seguir el rastro de un número hasta su origen.

Contexto de negocio

Cuando un gerente pregunta "¿por qué este número cambió?", necesitás responder en minutos. La arquitectura en capas es lo que da esa trazabilidad. Sin ella, cada incidencia es una investigación desde cero.

Escenario: lecturas de sensores (alta frecuencia) + datos de facturación (mensual) + maestros de plantas.

Arquitectura: Bronze recibe cada fuente por separado con su timestamp de ingesta. Silver normaliza unidades (m³, kWh), corrige lecturas fuera de rango y unifica la clave de planta. Gold expone fact_consumo (grano: planta × día) con dim_planta, dim_tiempo y dim_tipo_servicio.

Decisión clave: la lectura cruda se conserva en Bronze aunque parezca errónea — en industria regulada, poder demostrar qué informó el sensor es requisito de auditoría, no preferencia técnica.

04 Dos conceptos que te van a pedir siempre

Surrogate key vs. business key

La business key es el identificador del negocio (el código de planta, el email del cliente). La surrogate key es un ID artificial que genera tu warehouse (1, 2, 3…). Necesitás las dos:

  • La surrogate nunca cambia — si el negocio renombra un código, tus FKs no se rompen.
  • Joinear por un número es más rápido que por dos o tres campos de texto.
  • Permite historizar: un mismo business key puede tener varias versiones, cada una con su surrogate key.

04 Cargar desde GCS a BigQuery

Optimización de costos en BigQuery BigQuery cobra por TB escaneado. Para reducir costos: (1) particioná siempre por fecha, (2) filtrá por la columna de partición en cada query, (3) no usés SELECT * en tablas grandes, (4) clusterizá por las columnas más filtradas.

  • No usar particiones en MERGE. BigQuery escanea toda la tabla destino.
  • Permisos a nivel de proyecto. Alguien con acceso al proyecto ve todo. Usá IAM por dataset.

Estrategias de carga: INSERT, MERGE, OVERWRITE y CDC

Cómo cargar datos sin duplicar, sin perder y sin romper lo que ya funciona. La decisión más importante de un pipeline que nadie te enseña explícitamente.

Objetivo

Elegir la estrategia de carga correcta según el volumen, la frecuencia y el requisito de historización — y entender por qué INSERT INTO solo sirve en demos.

01 Las 7 estrategias comparadas

EstrategiaQué haceCuándo usarlaIdempotente
INSERT INTOAgrega filas al finalNunca en producción. Solo demos.No
INSERT OVERWRITEBorra todo y reescribeTablas pequeñas o reproceso completoSí
INSERT OVERWRITE + PARTITIONBorra solo la partición y reescribeTablas grandes, reproceso por día/mesSí
MERGE (UPSERT)Inserta nuevas, actualiza existentesDatos que cambian, carga incrementalSí
DELETE + INSERTBorra rango e inserta nuevoReemplazo de período sin historizarSí
CDC (Change Data Capture)Detecta cambios en el origen y replicaOrígenes transaccionales, near-real-timeSí
APPEND ONLY (eventos)Solo inserta, nunca borra ni actualizaEventos, logs, auditoríaSí

02 MERGE: la estrategia más usada en producción

MERGE compara el origen contra el destino por una clave. Si la fila existe, la actualiza. Si no, la inserta. Es idempotente: correrlo dos veces produce el mismo resultado.

⚠️ Error #1 con MERGE Si el origen tiene duplicados, el MERGE falla o comportamiento es impredecible. Siempre deduplicá el origen antes con ROW_NUMBER().

03 INSERT OVERWRITE por partición

Para tablas grandes donde reprocesar todo es imposible, sobrescribís solo la partición afectada.

04 CDC: Change Data Capture

Para orígenes transaccionales donde necesitás replicar cambios en tiempo real o near-real-time.

EnfoqueCómo funcionaHerramientas
CDC nativoEl motor de la base origen emite eventos de cambioDebezium, DMS (AWS), Datastream (GCP)
Snapshot + diffComparar snapshot actual vs anteriorSpark, dbt snapshots
Audit columnsEl origen tiene updated_at; solo traer lo que cambióCualquier ETL con filtro de fecha
Regla de decisión rápida
  • ¿Tabla pequeña (<1M filas) y reprocesable? → INSERT OVERWRITE
  • ¿Tabla grande, reproceso por día? → INSERT OVERWRITE + PARTITION
  • ¿Datos que cambian y necesitás el último valor? → MERGE
  • ¿Origen transaccional, necesitás near-real-time? → CDC
  • ¿Eventos que nunca cambian? → APPEND ONLY
Buenas prácticas
  • Nunca uses INSERT INTO en un pipeline agendado. Es la causa #1 de duplicación.
  • Siempre deduplicá antes de MERGE. El origen puede tener duplicados aunque vos no los pongas.
  • Usá una PK determinística (hash de campos clave) para el match del MERGE.
  • Testeá la idempotencia: corré el pipeline dos veces y verificá que los conteos no cambien.
  • Logueá cuántas filas se insertaron, actualizaron y eliminaron en cada corrida.
Errores comunes
  • MERGE sin deduplicar el origen. Falla silenciosamente o produce resultados erráticos.
  • OVERWRITE de toda la tabla cuando solo hace falta un día. Horas de procesamiento innecesarias.
  • No probar la idempotencia. "Funciona" la primera vez, duplica la segunda.
  • Usar MERGE cuando OVERWRITE basta. MERGE es más lento y complejo. Si no necesitás actualizar, no lo uses.

Glosario

Definiciones concisas de los términos que aparecen en cada fase del playbook.

Append-only
Estrategia de carga donde solo se insertan filas nuevas, nunca se actualizan ni borran. Usada para eventos y logs.
Arquitectura Medallion
Diseño en capas: Bronze (crudo), Silver (limpio), Gold (modelo de negocio). Permite trazabilidad y reproceso.
Business key (BK)
Identificador natural del negocio (ej: código de cliente, SKU). Puede cambiar con el tiempo.
CDC (Change Data Capture)
Técnica para detectar y replicar cambios en una base de datos origen hacia el destino, en tiempo real o batch.
Cluster
Conjunto de máquinas virtuales que ejecutan código en Databricks. Se apagan entre usos para ahorrar costos.
CTE (Common Table Expression)
Tabla temporal con nombre, definida con WITH. Permite organizar queries complejas en pasos legibles.
DAG (Directed Acyclic Graph)
Grafo dirigido sin ciclos que define el orden de ejecución de tareas en un pipeline. Una tarea solo corre cuando sus dependencias terminan.
Data Lake
Almacenamiento de datos en su formato original (CSV, JSON, Parquet), sin estructura previa. Cloud Storage y S3 son data lakes.
Data Warehouse
Base de datos optimizada para consultas analíticas. BigQuery, Snowflake, Redshift son warehouses.
Degenerate dimension
Atributo descriptivo que pertenece lógicamente a una dimensión pero se guarda directamente en la fact porque no tiene atributos propios (ej: número de factura).
Delta Lake
Formato de tabla que agrega transacciones ACID, time travel y MERGE sobre archivos Parquet. Nativo en Databricks.
Dimension (dim)
Tabla que describe el contexto de un hecho: quién, qué, dónde, cuándo. Ej: cliente, producto, tiempo.
ELT
Extraer, cargar y luego transformar. El dato crudo llega al warehouse y se transforma con SQL dentro de él.
ETL
Extraer, transformar y luego cargar. La transformación ocurre antes de escribir en el destino.
Fact (tabla de hechos)
Tabla central del modelo dimensional que guarda las métricas medibles: ventas, cantidades, eventos.
FK (Foreign Key)
Clave foránea: campo en una tabla que referencia la PK de otra tabla. En la fact, las FKs apuntan a las dimensiones.
Grano
Nivel de detalle de una tabla. "Una fila = un pedido × producto" define el grano de la fact.
Idempotencia
Propiedad de una operación que produce el mismo resultado si se ejecuta una o muchas veces. Fundamental en pipelines.
JOIN
Operación SQL que combina filas de dos tablas según una condición. LEFT JOIN conserva todas las filas de la izquierda.
Lakehouse
Arquitectura que combina la flexibilidad de un data lake con el rendimiento de un data warehouse. Databricks es la implementación más conocida.
MERGE (UPSERT)
Operación que inserta filas nuevas y actualiza las existentes según una clave de match. Idempotente si está bien implementado.
Metadata
Datos sobre los datos: quién los cargó, cuándo, desde qué fuente, en qué formato.
Notebook
Documento interactivo que mezcla código, texto y resultados. En Databricks y Jupyter.
Partición
División lógica de una tabla por una columna (generalmente fecha). Permite que las queries lean solo los datos relevantes.
PK (Primary Key)
Clave primaria: identificador único de una fila. En la fact, suele ser un hash determinístico.
Pipeline
Flujo automatizado de datos desde su origen hasta su destino, con transformaciones intermedias.
Reconciliación
Proceso de comparar los datos procesados contra la fuente original para verificar que no se perdieron ni duplicaron.
Reproceso
Volver a ejecutar un pipeline sobre un período histórico para corregir errores o aplicar nuevas reglas.
SCD (Slowly Changing Dimension)
Técnica para manejar cambios en las dimensiones. Type 1 sobrescribe; Type 2 conserva historial con vigencia.
Schema
Estructura de una tabla: nombres de columnas, tipos de datos y restricciones. En Databricks/GCP, también es un contenedor de tablas (equivalente a "database").
Star Schema
Modelo dimensional donde una fact está en el centro y las dimensiones la rodean, conectadas por FKs. Forma de estrella.
Surrogate key (SK)
Clave artificial generada por el sistema (1, 2, 3…) que nunca cambia. Se usa como PK de las dimensiones.
Time travel
Capacidad de consultar una tabla como era en un momento anterior. Nativo en Delta Lake y BigQuery.
Window Function
Función SQL que calcula sobre un grupo de filas relacionadas con la fila actual, sin colapsarlas. Ej: ROW_NUMBER(), LAG().
Workflow
En Databricks, un job que orquesta múltiples tareas con dependencias, schedule y alertas.
